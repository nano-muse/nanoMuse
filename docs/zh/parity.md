# 各客户端的功能对照

nanoMuse 在手机（Android、iOS）、电脑和浏览器中提供同一个智能体。桌面版是 Electron 外壳中的 `dsh-nanomuse` 插件包，网页版 nanoMuse Web 由运行时提供。运行时是实际执行任务的程序；Electron 是将网页界面封装为桌面 App 的框架。

从 0.1.32 起，项目以各端功能的并集为目标，即某个客户端支持的功能，其他客户端也尽量补齐。平台限制和有意的设计差异除外，例如电脑不需要手机内置的迷你 Linux，iOS 也不允许直接控制其他 App。本页对照已有功能，并记录尚待决定的差异。后半部分保留各版本的讨论与结论，已完成项目会注明版本。

本页的「手」指屏幕操作能力，「房间」指功能页面，hub 指同一账号的设备通信服务，MCP 指外部工具接入协议，OAuth 指服务授权登录流程。模型用量中的 token 是文本计量单位，访问令牌则是登录凭据，两者不同。更多说明见[术语表](glossary.md)。

图例：**✓** 已实现；**◐** 部分实现，缺少内容见备注；**—** 当前客户端不提供；**n/a** 不适用于该平台，不计划实现。

## 平台差异与决策记录 {#open-for-a-decision-the-next-next-list}

以下记录从 0.1.32 起的平台差异和待决事项。部分由系统限制决定，部分需要维护者选择实现方案。编号对应上表备注；已解决的条目仍保留，注明处理结果和版本。

1. **iOS 数据控制**。已于 0.1.33 完成，实现在 `NanoMuseDataControls.swift`。
2. **iOS 步骤显示**。顶部状态行和形象自 0.1.33 起已提供。关闭步骤显示时，进行中消息仍显示步骤，已完成消息隐藏步骤。待决定：既然状态行已说明当前工作，是否也隐藏进行中的步骤。
3. **iOS 请求 Star**。0.1.33 已将卡片固定在顶部下方。消息列表采用 `UICollectionView`，因此不能直接把卡片放到末条消息下。由于流式响应没有取消信号，取消轮次也计为完成。0.1.35 起按中继统一策略执行，见第 28 条：首次对话不请求，首次时机为第 3 个任务。
4. **iOS 首次引导**。0.1.34 已完成 `NanoMuseFirstRun.swift`，采用 Android 的 `needed / stage` 逻辑。未登录 Cloud 的用户都会看到引导，因此此前只用自有 key 的用户升级后也会看到一次，可通过「全部设置」跳过。
5. **Android OAuth 连接器的真机验证**。服务发现、动态客户端注册、PKCE 校验和 `Authorization` 请求头中的令牌处理均能编译，流程与桌面一致。但在 0.1.32 前没有完成连接器真机登录，构建机也没有模拟器。0.1.33 增加的 client-id 路径（GitHub、Slack 等）和浏览器交接也需要验证。密钥型和免登录连接器沿用普通 MCP 配置。令牌与 API key 一并保存在 `servers.json`，供沙箱内客户端读取；刷新发生在 App 启动或打开页面时，不在后台持续刷新。
6. **iOS 连接器**。0.1.33 已在 `NanoMuseConnectors.swift` 移植 Android 流程。与第 5 条相同，目前记录的验证仅为编译通过，仍需真机登录。
7. **网页连接器**。网页版已有手动添加 MCP 服务器的功能。若要提供授权登录，运行时必须自行执行 OAuth 流程并保存令牌；桌面由 harness 宿主完成。待决定：在运行时实现流程，利用已有 `nanomuse mcp` 桥接能力，还是通过账号下的桌面设备连接。
8. **桌面技能与编程助手页面**。harness 已有技能功能，不再重复提供技能页。「设置 → 编程助手」已完成，先显示本机 CLI 和聊天，再列账号的其他电脑。桌面自身通过 `src/coding.ts` 声明并处理 `coding.*` hub 动作，因此只安装桌面 App 的电脑也可被手机识别为编程设备。
9. **iOS 编程助手**。0.1.34 已通过 `NanoMuseCoding.swift` 和 hub 的 `coding.*` 动作完成。
10. **iOS 屏幕操作**。系统不允许一个 App 直接操控另一个，可用入口是 App Intents 和快捷指令，因此不计划实现通用「手」。0.1.36 已在设置中加入「Hands：iPhone 上不可用」，说明原因及账号下电脑可以提供的能力。iPhone App 保持打开时，可接收其他设备的 `task` 调用，例如 `@iPhone …`。
11. **iOS 主界面**。iPhone 的 Muse 外壳于 0.1.33 完成，0.1.34 起动态和目标由 `NanoMuseScheduler.swift` 实际调度，支持回前台补执行、`BGAppRefreshTask` 和到点的本地通知。iPad 也使用该外壳，外壳与顶部开关位于 nanoMuse 设置。工作室用自有百炼 key 生成，或使用运营者明确启用旧媒体代理的自建中继。限制是 iOS 后台刷新仅发提醒，不执行例程，界面会说明到点提醒用户打开。需要可靠执行时，应通过 hub 交给账号下的电脑。iPad 沿用放大的 iPhone 布局，0.1.35 已决定不单独做分栏。
12. **Android emoji 形象**。已能接收网页或桌面选择的 emoji 和颜色，重启、切换账号后仍保留。在手机上直接选择 emoji 是另一项待办。
13. **主题色色块**。0.1.33 已从桌面移除，统一规则为强调色随形象变化。
14. **Android 记忆页面**。手机将记忆放在设置中，其他客户端提供独立功能页。这是既定设计差异。
15. **桌面浏览器视图**。桌面在聊天轨迹中显示屏幕操作，不提供网页版式的页面查看器。这是既定设计差异。
16. **桌面和网页的接管**。0.1.34 两端均已通过运行时的 hold 机制实现暂停交接。代码为 `nanomuse/agent/holds.py`，`browser`、`computer_act`、`phone_act` 支持 `hand_over`，接口为 `POST /api/holds` 和 `/done`，事件为 `hold`。智能体最多等待十分钟，之后重新读取画面。桌面舞台提供「该你了」「好了」「我来接手」；网页允许接管后点击、输入、滚动、打开 URL，再点「完成」。iOS 无通用屏幕操作，因此没有相应交接，见第 10 条。
17. **桌面窗口外审批**。0.1.34 已在实时舞台提供「允许一次」「在 <app> 里始终允许」「拒绝」。主窗口不在最前时，置顶胶囊显示同一张卡片。Mac 上仍需验证 `showInactive` 不会抢走被操作 App 的焦点，测试项位于 `docs/tasks/mac-check-0.1.36.md` 的 D 部分。
18. **跨设备连接信息**。0.1.34 已完成。中继 0.17 的资料字段 `connectors` 按设备合并，最多 64 条，疑似密钥字段名会返回 400。四端均读写该字段，其他设备的连接显示为「已在 <device> 上连接，在这里登录」。凭据只保留在生成它的设备上。
19. **桌面操作与用户鼠标共存**。macOS 从 0.1.34 起参考 Codex 的窗口模式：`nanomuse/computer/mac_window.py` 在 `[hands] mode = auto` 下只截取目标窗口，并向其进程发送事件，用户仍能使用鼠标。每个 App 单独询问「让 <Muse> 使用 <App>？」。其他平台共享全屏，显示 UI-TARS 风格光晕，叠加提示不进入截图。Linux、Windows 尚无窗口模式，可考虑虚拟显示器或第二会话，先从成本较低的 Linux 开始。Mac 的 Quartz 接口路径需验证录屏回退、不依赖 AX（系统辅助功能接口）的点击、Retina 坐标映射和滚动方向。0.1.35 保留 `auto` 默认值：Quartz 层本身失败时，该目标后续步骤改用全屏并提示一次；窗口暂时消失则每次观察都重试；显式 `window` 模式持续尝试窗口。0.1.36 将 UI-TARS-desktop 操作器迁入 Electron 主进程，代码为 `harness/desktop/src/operator.ts`，使用 `@computer-use/nut-js`，经回环 HTTP 连接运行时的 `desktop` 后端。模型返回的截图像素坐标由 `nanomuse/computer/coords.py` 只映射一次，4K、缩放 2 的定位误差不超过 1 px。Mac 和 Windows 仍需验证打包后的原生插件、坐标单位（Mac 使用 point）、滚动单位、`ctrl` 到 ⌘ 的映射及内容保护，见 Mac 任务表 F 部分。
20. **没有公开远程 MCP 的服务**。0.1.34 已采用 nanobot 式聊天入口，让飞书、钉钉、企业微信和 Telegram 接收任务并回复。实现位于 `nanomuse/channels/`，使用厂商长连接 SDK 和配对码，不需要公网地址。SDK 是服务商提供的开发工具包。若要让智能体读取和操作服务内容，则需另做连接器。Zoom、LinkedIn、Zoho Invoice、WHOOP、腾讯文档、滴答清单、网易邮箱、QQ 邮箱和微信读书均需分别封装厂商 REST API，并申请开发者账号。待决定：哪些服务值得接入。
21. **Linux Wayland 屏幕操作**。当前截图和指针需要 X11 或 XWayland，直接在 Wayland 会话中会得到黑图并显示错误提示。X11 与 Wayland 是 Linux 的两种显示系统。0.1.36 起操作器的 `/info` 返回 `available: false` 并提示使用 Xorg 登录，「手」卡片会展示原因。UI-TARS-desktop 也未提供 Wayland 路径。通过 `xdg-desktop-portal` ScreenCast 和 `libei` 可探索原生支持，但每次会话需要权限对话框。是否优先实现仍待决定。
22. **手机聊天入口**。聊天入口在运行时中，网页及相应桌面页面已有配置界面。Android 和 iOS 仍需 `/api/channels` 客户端及开关、字段、配对码、已配对聊天、飞书二维码等卡片；接口和文案已准备好。是否放入下一版待决定。构建机尚未逐家完成真实连接，现有 SDK 调用仅离线对照正式包核验，公开宣布前需各建测试机器人。飞书发送者名称需要 `contact:user.base:readonly`，来自聊天入口的审批始终只适用一次。
23. **自有 key 的默认对话模型**。保存百炼或 OpenRouter key 后，候选由服务商 `/models` 决定。`deepseek-v4.1-flash` 不会自动置顶，目前只有 Cloud 模型组支持 `followPick`。建议在该模型可用时优先显示。
24. **推理 token 计量**。中继将推理 token 计入补全 token。如果服务商单独报告推理数量，且大于补全数量，则两者相加；否则视为已包含。若服务商单独报告且数量较少，会产生少计。待决定保留此推断规则，还是按服务商分别处理。
25. **桌面首次引导与首次对话**。0.1.35 已与手机一致：宿主保存 `firstrun.json`，新安装不跳过引导；App 先显示三句固定开场，不消耗 token，再询问称呼，并将模型 `nanomuse-naming` 代码块显示为起名卡片，移除 `take_name` / `ask_user_question`。既定差异是固定开场由客户端叠加、不保存为消息；称呼写入记忆而不修改 `GLOBAL.md`；首次引导的齿轮入口只在当前会话关闭引导。

29. **跨设备同一条对话**。0.1.36 已按 `docs/cloud.md` 的约定 C7 在中继 0.19 的 `/v1/sync/*` 保存聊天文字，登录后默认开启，各端「数据控制」可关闭或删除。每账号有一条主要聊天，设备自行执行的例程、目标、动态和受托任务不参与同步。0.1.37 的 C8 将各设备主要聊天按时间合并，远端轮次显示为「来自 Pixel 8」只读气泡，也交给模型读取。启用旁聊同步时，远端旁聊会成为本机聊天；用户消息发送即上传，回复在轮次结束上传，登录后回填历史。桌面将远端轮次追加到 dsh 日志，类型为 `user/message`，来源 `nanomuse-sync`，再由浏览器界面渲染。尚存限制：插件不支持删除，归档不会生成同步删除标记；远端删除的消息只隐藏，不从日志移除；关闭同步要等其他设备下次推拉时收到 `409` 才生效；iOS 的追加式存储会把迟到消息放在本地消息后。`@<device name>` 可请求另一设备执行，电脑需在线，手机需打开 App。iOS 直接发送 hub 提及，没有 `delegate` 工具，同时可自行响应 `task`。

34. **Android 使用中继建议**。原先 `AllowanceWaysCard` 只读取内置 `providers.json`，忽略 `/v1/me` 的 `spend.guidance`。原方案是在 `AllowanceWaysCard.kt` 和 `NanoMuseCloud.kt` 中优先使用 guidance，缺少时回退目录，与网页、桌面一致。0.1.40 已完成：`Guidance.kt` 解析，`Ways.resolve` 优先选用，卡片和「设置 → nanoMuse Cloud」共用结果。
35. **手机拒绝提示与运营开关**。早期 `describe` 能识别额度、每日上限、限流、错误 key、停用账号和上游故障，但缺少 `too_large`（413）、`not_invited`、`too_many_in_flight`、`provider_busy`，以及中继 0.22 的 `service_paused`、`sync_paused`、`hub_paused`、`signup_closed` 和 `paused: true` 的 `allowance_exhausted`。结果是用户看见原始英文，或将暂停误当耗尽。网页和桌面 0.1.40 的参考实现在 `nanomuse/server/failures.py` 和 `harness/dsh-nanomuse/src/refusals.ts`，提供中英文句子。手机也已于 0.1.40 补齐九种代码：`RelayRefusal` / `NanoMuseRelayRefusal` 分类，`describe` 转换，各语言均有文案。iOS 拒绝轮次也走同一路径，卡片分别提供「新对话」「登录」「打开设置」「再试一次」，暂停额度与耗尽使用不同说明。
36. **桌面和网页语音**。听写依赖 Web Speech API，它是 Chrome 内的 Google 服务，Electron 不自带，因此桌面打开听写说明页，网页仅在支持它的浏览器中可用。两端目前均不朗读回复。提议经运行时 `/api/speech` 统一处理语音输入输出，使用自有 key 或中继的模型，例如百炼 `paraformer` / `cosyvoice`、OpenAI `whisper` / `tts`；手机继续用系统语音引擎。
37. **网页数据导出**。桌面通过 `/data/export` 把智能体数据 zip 写入「下载」，网页早期只有形象分享和数据控制。该缺口现已解决：`nanomuse/server/data_export.py` 在内存中打包 `profile.json`、各功能页、通讯录、授权、`threads/`、`sessions/` 及说明各部分的 README。`GET /api/data/export` 直接返回文件，带 `Cache-Control: private, no-store`，异机浏览器也可下载，运行时磁盘不落文件。压缩包不包含 `vault.enc`、`vault.key`、`server_token`、`push-vapid.json`、设置、`logs/`、`workspace/`，单文件超过 64 MB 时跳过，与桌面一致。入口为「设置 → 数据控制 → 下载你的智能体数据」。
38. **界面语言**。手机跟随系统，Android 为 17 种、iOS 为 9 种；网页可在 App 中选择自动、en、zh-CN；桌面通过 harness 语言设置支持英文、中文。提议按用户需求扩展桌面 `locales.ts`，先考虑 de（德语）和 ja（日语）；手机应用内语言覆盖由上游决定。
39. **网页首次对话**。已与手机交互一致，由运行时保存状态。`nanomuse/server/firstrun.py` 管理阶段、附加提示词和存储，状态在资料旁的 `firstrun.json`；`nanomuse/fences.py` 解析代码块；路由为 `/api/firstrun*`，WebSocket 消息为 `firstrun`。`web/src/components/FirstConversation.tsx` 显示三句开场和起名卡片，引导清单已移除单独的「认识你的 nanoMuse」页。称呼同时写入资料和「Call them: …」记忆，运行时不使用 USER.md。身份表单仍在设置中供后续修改。约定补充保存点击「开始」时的 `lang`，保证模型附加提示中的开场与用户看到的一致。完整流程见 [web.md](web.md#the-first-run-and-the-chat-s-opening)。
40. **四项模型用途设置，0.1.41**。Android、iOS 和桌面使用统一模型页，保存 key 后提供「用它来做什么」，自有模型对话或屏幕失败后提供「这次改用 nanoMuse Cloud」。网页在「连接」中提供同样四项，由 `PUT /api/connections/gui`、`/image`、`/video` 配置，均支持「自动」，1.0.1 起也支持失败轮次改用 Cloud。网页暂未提供用途卡片，自有 key 表单设置对话来源，图片和视频在各自行配置。项目托管 Cloud 不提供媒体生成。iOS 图片和视频目前仅支持 DashScope API，因此只列阿里云百炼等 DashScope 地址上的自有服务商。后续可按需求补网页用途卡片和 iPhone 的 OpenAI 图片接口。
41. **在其他设备上开始对话（#815）**。Android、桌面版和 iPhone 均可在「新建对话」中选择目标设备，iPhone 的 Muse 聊天抽屉也提供「电脑」入口。每个对话按设备 ID 记住目标，即使目标离线也能保留独立草稿。Android 和桌面版可作为持久任务的执行设备，iPhone 可向支持此功能的设备发起任务。

## 如何维护这份对照表 {#keeping-this-true}

- 连接器目录以 `harness/dsh-nanomuse/src/connectors-catalogue.ts` 为唯一来源。运行 `node scripts/connectors-json.mjs` 生成 Android 和 iPhone 的副本。harness 工作流以 `--check` 检查，任何副本过期都会失败。
- 自有 key 服务商目录以 `nanomuse/llm/providers.json` 为唯一来源。`node scripts/providers-json.mjs` 生成桌面、中继和手机副本，`--check` 检查是否过期。新增服务商、修改端点或能力时，只编辑源目录。
- 四端使用同一份通信数据格式。对应实现为运行时的 `nanomuse/cloud.py`、桌面的 `harness/dsh-nanomuse/src/relay.ts`、Android 的 `io.github.nanomuse.cloud.NanoMuseCloud`、iOS 的 `NanoMuse/NanoMuseCloud.swift` 和 `NanoMuseAccount.swift`。中继增加字段时，四处都需同步支持。
- `docs/cloud.md` 中的中继拒绝代码需在四处转换为用户提示：运行时和网页的 `nanomuse/server/failures.py`，桌面的 `harness/dsh-nanomuse/src/refusals.ts`，以及 Android、iOS 的 `NanoMuseCloud.describe`。桌面由宿主转换错误，客户端展示卡片。新增代码要同时更新四处及各客户端已有语言，可参考桌面 `tests/refusals.test.mjs` 和 `tests/refusal-card.test.mjs` 的测试方式。
- 各端按中继 `/v1/nudges` 的同一策略请求 Star，见 `docs/cloud.md` 约定 C1，内置默认值也相同。「任务」仅指用户发起并获得回复的一轮，不计首次对话、例程、动态和目标检查。每个时机请求一次，请求间隔为 `cooldown_days`，每台设备最多 `max_asks` 次。点击「去 GitHub 点亮 Star」或「已经点过了」均保存 `nm.star.*` / `nanomuse.star.*` 标记，无论冷却时间和剩余次数如何，本机都不再请求。设置与关于页的 Star 入口也设置相同标记。此标记不随账号同步，其他设备需各告知一次。实现在 `nanomuse/nudges.py`、`harness/dsh-nanomuse/src/nudges.ts`、`web/src/nudges.ts`、`io.github.nanomuse.community.Nudges`、`NanoMuse/NanoMuseNudges.swift`。
- 各端版本检查统一先读取 `https://nanomuse.cn/dl/index.json`，再查询 GitHub `releases/latest`，缓存一天。检查行始终同时显示已安装版本。
- 对话同步遵守 `docs/cloud.md` 约定 C7，四端与中继使用相同数据格式。代码分别为 `cloud/nanomuse_cloud/sync.py`、运行时和网页的 `nanomuse/sync/`、桌面的 `harness/dsh-nanomuse/src/sync.ts`、Android 的 `io.github.nanomuse.sync`、iOS 的 `NanoMuse/NanoMuseSync.swift`。每批数据先应用对话信息，再应用消息；仅在拉取时推进游标，即记录已读取的位置。只上传用户消息和最终答复，不上传工具步骤、工具结果或系统提示。例程、目标、动态和受托执行留在本机。
- `ideas.en.json` / `ideas.zh.json` 在 Android 资源、iOS Resources、`harness/dsh-nanomuse/assets` 和 `web/src/ideas` 中各存一份相同副本。任一副本不一致时，harness 和网页测试都会失败。
