# 目标评测任务

这组评测包含十项中文任务，涉及费用报表、车票筛选、会议简报、日历和文件归档。每项任务都在独立的模拟环境中执行。运行时的目标评估器会根据实际产生的数据和最终回答判断结果，而不是直接相信模型说「完成了」。

这里的运行时是执行智能体任务的程序；评估器是检查任务是否满足预设条件的组件。离线回放指重复使用已录制的模型回答，不向模型服务发起新请求。

## 离线回放 {#offline-replay}

CI（自动执行检查的持续集成流程）运行 `pytest -q -m "not live"`。测试会禁止联网，使用已录制的模型回答执行任务。

当前录制数据来自 2026 年 11 月 1 日的 `deepseek-flash`，只保存模型回答和服务商报告的用量，不包含发给模型的输入或模型的推理内容。如果修改了智能体的执行循环，可能需要重新录制，因为测试消耗的回答数量必须与录制数据完全一致。

## 使用自己的模型 {#run-with-your-model}

按[配置说明](configuration.md)设置服务商、模型和密钥，然后运行：

```sh
NANOMUSE_LIVE=1 NANOMUSE_GOAL_EVAL_OUTPUT=./goal-eval-output \
  python -m pytest -q -m live tests/test_goal_eval_tasks.py
```

测试会调用你配置的模型，关闭重试，并将每项任务限制在 50000 token 和 120 秒以内。token 是模型计算输入、输出和用量的文本单位，不等同于字数；这些调用可能产生服务商费用。

`NANOMUSE_GOAL_EVAL_OUTPUT` 指定结果保存目录。不设置时，文件写入 pytest 的临时目录。`report.json` 保存判定结果和可取得的用量，`recording.json` 保存模型回答。用新录制数据替换 `tests/fixtures/goal_eval/tasks_v1_recording.json` 前，先检查文件是否包含个人信息或密钥。替换后重新运行离线测试，逐项核对判据结果的变化。

结果中的 `verified` 表示这项任务的固定判据与实际观察结果相符。`partial`（部分满足）、`unknown`（无法确定）和 `contradicted`（观察结果与判据矛盾）也只描述这些判据，不能直接代表模型的整体能力。检查规则可能识别不了同义表达，也可能误读文本；这十项任务的表现不能推广到其他任务。live 测试只要求评测程序运行结束，不要求模型成功完成任务。

费用总额保留正负号和小数部分。如果出现互相矛盾的总额，或者数值无法在不损失精度的情况下表示，结果会保持 `unknown`，不会判为通过。

`tasks_v1.json` 中的预期结论对应仓库当前保存的模型回答。更新录制数据后，先人工逐项核对发生变化的结论，再更新预期值。

## 判据用例 {#criterion-cases}

`criteria_cases_v1.json` 用来衡量评估器本身。每条用例构造最终状态和回答，把一条判据
跑到结论，再和预期比对。来源为 `spec` 的用例由另一个模型只看规则、在空目录里写成；
来源为 `code` 的用例对着评估器代码写，专找它会判错的输入。每条判据至少有一条应通过
和一条应不通过的用例。

`expected` 按判据定义给出。`current` 固定评估器目前仍判错的结果，即已知漏判。判据
照规则判对了、仍达不到用户目标时，`truth` 记下用户目标：比如日历事件建对了，回答里
报的时间却是错的。补上这类缺口要新增判据，留到下一版任务。改动使某条用例的结果变化
时，在同一个提交里更新这条用例。

读取回答的判据不会猜测否定的意思。如果同一分句中既有结果或车次排除词，又有不、未、没、
无，且否定字不在该分句的任何状态词或排除词里，判据就记为 unknown。用例也记录了这条
规则的代价：例如如实说明“因无权限被拒”，也会转人工复核。
